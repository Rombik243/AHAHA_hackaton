# Procurement Scout

Backend для подбора поставщиков по закупке. Режим извещений и ТРУ ищет кандидатов
в загруженной истории и через настроенный веб-поиск; файл исторических участий поставщиков
необязателен. Кандидаты возвращаются без рейтинга, для дальнейшей работы ML.
Существующий режим одного CSV/JSON с веб-поиском и ранжированием сохранён.
Интерфейс для frontend — REST API и Swagger.

## Проверка предложений по позициям ТРУ

Все временные лимиты задаются в корневом `.env`; после изменения перезапустите API:

```dotenv
TEST_MODE=true
MAX_RUN_SECONDS=180
OLLAMA_TIMEOUT=60
OLLAMA_RETRIES=1
REQUEST_TIMEOUT=15
```

`MAX_RUN_SECONDS` ограничивает весь тестовый run, включая очередь фоновой обработки, поиск,
загрузку страниц и вызовы Ollama. По истечении run получает `status=completed`,
`stage=partial_timeout` и предупреждение о лимите; уже сохранённые частичные результаты доступны
через API. CSV `relevant/audit/offers` для поиска также доступны на момент остановки.
Run перестаёт расходовать время, API и следующие запросы продолжают работать. Отключите
общий тестовый лимит значением `TEST_MODE=false`. `OLLAMA_TIMEOUT` ограничивает один запрос
к модели, `OLLAMA_RETRIES` — число повторов после ошибки, `REQUEST_TIMEOUT` — HTTP-запросы
к поиску/страницам. Пример тестового профиля: `MAX_RUN_SECONDS=120`, `OLLAMA_TIMEOUT=30`,
`OLLAMA_RETRIES=0`, `REQUEST_TIMEOUT=8`.

Новые запуски `/suppliers/search`, `/suppliers/bulk` и `/runs` с извещениями/ТРУ
содержат дополнительный объект `relevance` в `/runs/{id}/results`. Существующие
`notices`, `candidates`, `search_stats` сохранены. `candidates` — общий пул, включая
исторические связи; подтверждение подходящего предложения находится в `relevance.decisions`.
Обогащение `/suppliers/enrich` и старое ранжирование работают отдельно.

```json
{
  "query": "Поставка бумаги для офиса",
  "region": "Санкт-Петербург",
  "items": [{
    "target_item_id": "paper-1",
    "product_name": "Бумага A4",
    "offer_type": "product",
    "okpd2_code": "17.12.14.110",
    "attributes": [{"name": "плотность", "value": "80", "unit": "г/м²", "required": true}]
  }]
}
```

`items` заменяет старые списки `products`/`okpd2_codes`, когда передан; позволяет явно
связать код, товар и требования. `offer_type`: `product`/`service`. Идентификаторы
позиций генерируются, если не заданы. Регион берётся из запроса, иначе
`DEFAULT_DELIVERY_REGION=Санкт-Петербург`; `region_origin` показывает `request/default`.
CSV сохраняет обязательные старые столбцы и разделитель `;`: в извещениях разрешён
дополнительный `delivery_region`, в ТРУ — `target_item_id`, `offer_type`, `attributes`
(JSON-массив с правильным CSV-экранированием кавычек). В multipart `/runs` и `/suppliers/bulk`
можно передать общий `region`. Одинаковые строки ТРУ представляют отдельные позиции.

Структура `relevance`:

- `targets`: требования каждой позиции, исходный ОКПД2, регион и его происхождение;
- `pages`: заголовок, время загрузки, контрольная сумма сохранённого текста,
  JSON-LD, фрагменты и журнал входов модели, все найденные ИНН с контекстом и checksum;
- `offers`: отдельные товары/услуги и варианты, исходные характеристики/единицы,
  факты с областью действия, URL, цитатой, временем и методом; опубликованные и
  предположенные моделью ОКПД2 хранятся раздельно;
- `decisions`: решение каждой пары позиция/предложение, `match/mismatch/unknown/not_required`
  по критериям, причины, доказательства, версии схемы/промпта/модели, digest при доступности;
- `coverage`: покрытие позиций каждой компанией со ссылками на предложения; это не рейтинг;
- `is_ground_truth=false`: автоматические результаты не являются экспертной ML-разметкой.

Статусы: `relevant` требует подтверждённых обязательных условий и связи с продавцом;
`needs_review` сохраняет недостаток/неоднозначность/конфликт; `irrelevant` — явное
несоответствие; `processing_error` — ошибка поиска, загрузки, модели или схемы.
Контрольная сумма ИНН не подтверждает регистрацию компании. Факт на сайте не считается
независимо проверенным. ИНН из общего подвала, домен каталога и офисный адрес сами по себе
не доказывают продавца, официальный сайт или доставку. Неподтверждённая компания остаётся
`null`, варианты ИНН доступны в аудите. Числовые характеристики нормализуются без
выдуманных единиц и автоматического признания эквивалентности материалов.

Экспорт `/runs/{id}/export` для новых запусков с `relevance`:

| layout | Содержимое |
|---|---|
| `relevant` (по умолчанию) | Только технически проверенные релевантные предложения |
| `audit` | Остальные статусы, причины, включая ошибки без найденного предложения |
| `offers` | Все решения по всем позициям |
| `pool` | Старый общий пул кандидатов, одна строка на ИНН |
| `matches` | Старые связи кандидатов с закупками |

Детальный CSV: `target_lot_id + target_item_id + supplier_inn + offer_id + source_url`,
UTF-8 BOM, разделитель `;`. Неизвестные значения — `null`, пустые массивы — `[]`.
Вложенные поля — JSON; `decision_json`, `offer_json`, `target_json` сохраняют точные
объекты ответа API для обратного чтения. Текстовые ячейки, похожие на формулы, экранируются.
Старые сохранённые запуски без `relevance` сохраняют прежний экспорт по умолчанию.

`GET /runs/{id}/pages/{page_id}` отдаёт сохранённый текст и JSON-LD для аудита/повторной
обработки. Архив — gzip по хешу, `PAGE_ARCHIVE_PATH`, общий предел
`MAX_PAGE_ARCHIVE_BYTES` (500 МБ). При исчерпании лимита сохраняется явная ошибка,
тексты автоматически не удаляются. Для переноса результатов переносите также архив.
`observed_at` — время получения, а не дата публикации или гарантия актуальности.

Обход ограничен `MAX_PAGES_PER_LOT` и `MAX_RELATED_PAGES` (контакты, доставка, каталог
того же хоста). Каждая загруженная страница разбивается на фрагменты; при превышении
`MAX_RELEVANCE_CHUNKS_PER_PAGE` выбираются фрагменты по всей длине и ставится признак
неполноты. JavaScript не исполняется, динамика/капча/пропуски помечаются. Отсутствие
предложения в HTML не означает отсутствие товара у поставщика.

Ollama получает явный `num_ctx=RELEVANCE_CONTEXT_TOKENS` (32768), чтобы большой JSON-контракт
не обрезал вход обычным небольшим контекстом. Эта настройка требует памяти; для небольшого
компьютера согласованно уменьшайте контекст, размер фрагмента и число переданных символов.
Вызовы последовательны, ограничены `OLLAMA_TIMEOUT` и `OLLAMA_RETRIES`; ошибки доступны в аудите.

Офлайн-проверки: `python -m pytest -q`. Отдельная проверка настоящей Ollama на явно
вымышленной, заранее размеченной разработческой выборке (не live-поиск):

```powershell
.\.venv\Scripts\python.exe scripts/evaluate_offer_relevance.py --cases tests/fixtures/offer_relevance_cases.json --output tmp/offer_eval.json --limit 3 --timeout 120
```

Скрипт сохраняет промежуточные результаты после каждого случая, ошибки, ложные включения,
пропуски релевантных, заполненность/точность полей и буквальность цитат. Метки этой небольшой
Codex-составленной выборки не заменяют независимую экспертную разметку для обучения.

**По умолчанию включён полностью автономный demo-режим.** Компании и источники в
`data/` вымышлены. Они нужны для проверки pipeline и обозначены в API как demo.
Ollama, поисковый ключ и интернет для демонстрации не требуются.

## Массовый сбор и поиск по одному запросу (без ранжирования)

### Обогащение списка для ML

`POST /suppliers/enrich` принимает multipart/form-data:

- `suppliers` — обязательный CSV с разделителем `;`. Обязательная колонка: `supplier_inn`.
  Необязательные: `supplier_kpp`, `supplier_name`, `website`, `lot_id`, `is_winner`, `is_demo`.
  Исходный формат `lot_id;supplier_inn;supplier_kpp;is_winner` тоже принимается.
- `notices`, `tru` — необязательные исторические CSV описанного ниже формата. Загружаются
  только записи, связанные с выбранными поставщиками по `lot_id`; они сохраняют контекст для ML.
- `supplier_inns` — необязательный JSON-массив строк, например `["7707049388","7605016030"]`.
  Пустое поле означает всех поставщиков в рамках установленного предела пакета.

Пример заголовка простого справочника: `supplier_inn;supplier_kpp;supplier_name;website`.
Кавычки, переносы внутри ячеек, UTF-8/BOM и Windows-1251 поддерживаются. Идентификаторы
сохраняются строками. Пропущенный/некорректный ИНН пропускается с предупреждением;
ошибочная структура, КПП и флаг победителя дают 422. Демо-строки и `.invalid` исключаются.
В историческом поле `is_eshop_or_aisgz` допускаются как прежние булевы значения, так и
названия систем из файлов 24–25 (`АИС ГЗ`, `ЭМ`), без придумывания их числовой кодировки.

Новый импорт читает файлы потоково. `MAX_ENRICHMENT_UPLOAD_BYTES=512000000` применяется
к каждому из трёх файлов и позволяет загрузить исходные файлы 24–25 без их разрезания.
За один запуск допускаются `MAX_ENRICHMENT_SUPPLIERS=1000` уникальных ИНН и
`MAX_ENRICHMENT_RECORDS=100000` выбранных строк поставщиков/ТРУ. Превышение даёт 422
с предложением выбрать пакет через `supplier_inns`, а не незаметное усечение результата.
Размер файлов для прежних `/runs` и `/suppliers/bulk` регулируется прежним `MAX_UPLOAD_BYTES`.

Для каждого ИНН выполняется поиск реквизитов/контактов и каталога через настроенный
SearXNG/Brave, а также загрузка переданного `website`, если он есть. Обрабатываются до
`MAX_ENRICHMENT_PAGES_PER_SUPPLIER=4` страниц. Страница с другим, отсутствующим или
несколькими ИНН не приписывается поставщику. На подходящих страницах обычный код извлекает
подписанные реквизиты и контакты, Ollama — название, адрес, товары/услуги, регионы,
сертификаты, лицензии и специализацию. Сохраняются только сведения с цитатой из страницы.
Недоступность LLM сохраняет подписанные реквизиты; недоступность поиска сохраняет весь
входной список и объяснение пропусков. Контактные страницы автоматически не обходятся:
для лучшего покрытия можно передать их URL в `website` или получить их через поиск.

Ответ 202 содержит `run_id`, `status_url`, `results_url`, `export_url`. JSON результата
содержит прежние `notices`, `candidates`, `search_stats`, `run`, а у каждого кандидата:

- `origins`: `preloaded`, `parser_discovered` или оба значения;
- `input_records`: все исходные строки, их `original` значения, файл и номер записи;
- `observations`: тип/значение, `source` (URL или файл/строка, цитата, время),
  `origin`, `method` (`upload`, `regex`, `llm`), `status` (`input_provided`, `source_supported`);
- `enrichment`: статус `pending/completed/partial/unavailable`, число обработанных страниц,
  предупреждения и `fields` со статусом `found/input_only/unknown/conflict` и причиной.

Статус `completed` у запуска означает завершение обработки; проверяйте также статусы
отдельных поставщиков. Несколько контактов/КПП сохраняются как наблюдения. Исходное имя
и сайт имеют приоритет для отображения, найденные альтернативы остаются в `observations`.
Разные названия/сайты отмечаются как конфликт. `source_supported` означает наличие
сведения на странице, а не проверку регистрации, лицензии или владельца сайта.
`observed_at` — время получения/импорта, не дата обновления источника. Поле `website`
из CSV имеет статус `input_only`, пока не найдено подтверждение; домен поискового
результата сам по себе не назначается официальным сайтом. Веб-адрес извлекается только
из явно подписанного «официальный сайт»/«сайт компании» на странице с однозначным ИНН.

### Добавление новых поставщиков к результату

В `POST /suppliers/search` передайте `base_run_id` завершённого запуска:

```json
{
  "query": "Поставка упаковочных материалов",
  "region": "Санкт-Петербург",
  "products": ["Коробки картонные"],
  "okpd2_codes": [],
  "base_run_id": 12
}
```

Замените `12` своим `run_id`. Новый запуск содержит исходный список и всех найденных
кандидатов с ИНН, объединённых по ИНН. Предыдущий запуск не изменяется. Сохраняются все
связи с закупками и источниками, совпавший поставщик получает оба происхождения.
Поставщики исходного списка остаются даже без совпадения с новым запросом; связи с новым
запросом появляются только у найденных кандидатов. Разные ИНН на одном домене не сливаются.
Без `base_run_id` сохраняется прежнее поведение поиска.

В обоих CSV (`pool`, `matches`) добавлены JSON-колонки `origins`, `input_records`,
`observations`, `enrichment`. `pool` — одна строка на ИНН и формат по умолчанию для enrich.
В `matches` поставщик без закупок тоже выгружается отдельной строкой с пустыми полями
связи. Все новые поля доступны также через `/runs/{run_id}/results`. Score и rank не
вычисляются; `matched_by=text` для web означает обнаружение текстовым запросом, а не
подтверждённое соответствие всем требованиям закупки.

В `matches` колонки `input_records` и `observations` содержат сведения источника данной
строки. Полный профиль со всеми наблюдениями находится в `pool` и JSON кандидата;
объединяйте его со связями по `supplier_inn`. Это исключает повторение всей истории
поставщика в каждой строке большого экспорта.

Для поиска по закупкам в Swagger доступны ручки в разделе **Suppliers**:

| Ручка | Вход | Результат |
|---|---|---|
| `POST /suppliers/bulk` | Файлы `notices`, `tru`; `suppliers` необязателен | Все извещения, общий CSV: одна строка на уникальный ИНН |
| `POST /suppliers/search` | JSON с одним `query`, необязательные `region`, `products`, `okpd2_codes` | Кандидаты и основания совпадения только для одного запроса |

Обе ручки возвращают HTTP 202 и `run_id`, `mode`, `status_url`, `results_url`, `export_url`.
Сбор идёт в фоне. Проверяйте `status_url`; после `status=completed` скачайте CSV по
`export_url`. По `results_url` доступны JSON и промежуточные результаты. Ни одна из этих
ручек не вычисляет score, не ранжирует и не обрезает список найденных кандидатов.
Число исследуемых страниц ограничено настройками поиска, описанными ниже.

**Массовый сбор:** загрузите извещения в `notices` и ТРУ в `tru`. Все уникальные
извещения обрабатываются; фильтра `target_lot_ids` здесь нет. `suppliers` можно оставить
пустым — новые компании ищутся в интернете. Исторические закупки/участия нужны только
для дополнения поиска историческими совпадениями. Все таблицы связываются по `lot_id`.

**Один запрос:** в `POST /suppliers/search` отправьте, например:

```json
{
  "query": "Поставка офисной бумаги A4, 80 г/м²",
  "region": "Казань",
  "products": ["Бумага офисная A4"],
  "okpd2_codes": []
}
```

Достаточно одного поля `query`; неизвестный ОКПД2 можно не задавать. Регион используется
в поисковой фразе, а не как подтверждённая география поставщика. Создаётся ровно одна
целевая закупка с техническим `lot_id=user-query`. Результаты других запусков не
подмешиваются. Для старых клиентов сохранён `POST /runs` с прежними полями; его
`target_lot_ids` принимает JSON-массив строк, например `["000123"]`, либо не передаётся.

Заголовки двух обязательных файлов и необязательного файла поставщиков (разделитель
**`;`**, порядок столбцов произвольный):

```text
# notices
publish_date;procedure_id;lot_id;start_price;reqnum;procedure_name;subject;is_smp;customer_inn;customer_kpp;is_eshop_or_aisgz
# tru
lot_id;product_name;okpd2_code
# suppliers (необязательно)
lot_id;supplier_inn;supplier_kpp;is_winner
```

Строки `# notices` / `# tru` / `# suppliers` выше — подписи, в CSV их добавлять не нужно.
Поддерживаются UTF-8 (с BOM или без) и Windows-1251, кавычки, `;` и переносы строк
внутри кавычек, пустые ячейки. `lot_id` обязателен. Остальные пропуски остаются `null`.
ИНН, КПП, номера процедур/регистрации и ОКПД2 хранятся строками с ведущими нулями.
ИНН поставщика должен содержать 10 или 12 цифр и не состоять из нулей; иначе строка
участия пропускается с предупреждением. Проверка наличия ИНН в исходной строке и
формата не является проверкой регистрации компании или контрольных цифр.
КПП — 9 цифр. Флаги: `true/false`, `1/0`, `да/нет`, без учёта регистра; пусто — `null`.
Даты: ISO 8601 либо `ДД.ММ.ГГГГ` (допустимо время `ЧЧ:ММ:СС`). Цена неотрицательна,
поддерживает десятичную запятую/точку и пробелы между разрядами; в JSON отдаётся
десятичной строкой, без потери точности. Неизвестные/повторные колонки, неверная структура,
типы и конфликтующие извещения с одинаковым `lot_id` дают HTTP 422 с местом ошибки.
Некорректный ОКПД2 пропускается с предупреждением, текст ТРУ сохраняется.

Поиск использует объединение трёх оснований:

- участие в самом целевом лоте, если оно есть во входных данных;
- совпадение ОКПД2: точное, по иерархии (короткий код — префикс полного) или категории
  первых пяти цифр; короткие коды не дополняются нулями;
- текстовое сходство названия процедуры, предмета закупки или любой позиции ТРУ.
  Переиспользуется подход TF-IDF по символьным n-граммам из поиска истории.

Достаточно одного основания. Ранжирование не вызывается, top-k нет. Порог только для
текстового извлечения `CANDIDATE_TEXT_MIN_SIMILARITY=0.08`; он не ограничивает совпадения
по коду и участие. Общие слова вроде «поставка» сами по себе не создают совпадение.
Каждая позиция ТРУ участвует в поиске отдельно, чтобы смешанный лот не скрывал малую позицию.
Текстовый индекс строится один раз на запуск; сходство считается разреженно по одной
целевой закупке. Поиск для всех лотов может дать очень большой результат; в старом
`POST /runs` для ограничения области доступен `target_lot_ids`. Лимит `MAX_UPLOAD_BYTES` применяется к каждому файлу
(по умолчанию 5 МБ). Это обработка загруженного корпуса в памяти, не потоковый импорт
многомиллионной базы.

Источник кандидатов — найденные в интернете страницы, загруженные таблицы участий,
а также реальная история из явно настроенного
`HISTORY_PATH`, если он отличается от комплектного `data/history.csv`. Используется
существующий формат истории (`lot_name`, `description`, `okpd2`, `company_inn`, при наличии
`lot_id`, `supplier_kpp`, `is_winner`). Демо-история из `data/` не открывается; записи
`is_demo=true`, сайты `.invalid` и записи без корректного ИНН исключаются. Для веб-поиска
задайте `WEB_SEARCH_PROVIDER=searxng` (или `brave`) и `LLM_ENABLED=true`: поисковик находит
страницы, а локальная Ollama извлекает название компании. Кандидат попадёт в ответ только
при наличии на странице подписанного ИНН с точной цитатой. В источнике ответа указываются
URL страницы, цитата и время получения. КПП берётся со страницы, только если явно подписан;
победитель для веб-кандидатов остаётся `null`, поскольку поиск страницы не подтверждает
участие компании в историческом лоте.

Пример вызова из PowerShell (пути замените на свои):

```powershell
curl.exe -X POST "http://127.0.0.1:8000/suppliers/bulk" -F "notices=@C:/data/notices.csv" -F "tru=@C:/data/tru.csv"
```

Адреса статуса/результатов/экспорта общие: `/runs/{id}`, `/runs/{id}/results`,
`/runs/{id}/export`. `run.mode` равен `suppliers_bulk`, `suppliers_search` или
`candidates` (старый `POST /runs` с CSV извещений).
Результат `GET /runs/{id}/results` имеет поля:

```text
run: статус, предупреждения, время запуска
notices[]: выбранные извещения со всеми исходными полями, source и связанными tru[]
search_stats[]: статистика веб-поиска по каждому target_lot_id
  status: completed / partial / unavailable
  queries, pages_found, pages_processed, candidates_found
  search_errors, extraction_errors, unverified_pages, page_limit_reached
candidates[]:
  supplier_inn: строка, один объект на ИНН во всём запуске
  matches[]:
    target_lot_id, target_procedure_id, target_reqnum: исходное целевое извещение
    lot_id: найденный лот, в котором зафиксировано участие
    supplier_kpp, is_winner: значения из строки участия найденного лота либо null
    matched_by: participation / okpd2 / text
    okpd2_matches[]: requested_code, found_code, relation
    procedure_name, subject, tru[]: сведения о найденной закупке
    source: kind (web/upload/history/request), URL, цитата, время получения либо файл и строка
    notice_source: источник найденного извещения, если он есть
```

`row` — номер CSV-записи с учётом заголовка (2 — первая запись); для JSON-истории — номер
объекта начиная с 1. Многострочное поле считается частью одной CSV-записи.
КПП и признак победы находятся в `matches`, поскольку у
одного ИНН они могут отличаться по лотам. Веб-совпадение связано с поисковым запросом
(`search_query`); у него нет исторического `lot_id`. Конфликтующие наблюдения сохраняются отдельными
связями. Историческая победа **не означает** победу в целевой закупке, выполнение контракта
или подтверждённую возможность поставки всех товаров смешанного лота. Названия/коды
в `tru` описывают найденный лот; точные пары совпадений кодов — в `okpd2_matches`.
Все даты корпуса доступны поиску; для временной ML-валидации подавайте заранее ограниченную
историю. Даты публикации не используются как фильтр в этом режиме.

CSV-экспорт: UTF-8 BOM, разделитель `;`. Общая таблица `layout=pool` содержит
**одну строку на каждый уникальный ИНН всего запуска** (для новых запусков её нужно выбрать явно).
Столбцы: `supplier_inn`, `supplier_name`, `supplier_kpp`, `website`, `supplier_names`,
`supplier_kpps`, `websites`, `target_lot_ids`, `target_notices`, `source_urls`, `sources`,
`matches`. Массивы сериализованы в JSON. В `matches` сохранены все связи, основания
совпадений и исторические признаки победителя. Если названия, КПП или сайты расходятся,
одиночное поле пустое, все исходные варианты остаются в соответствующем массиве.

Для старых сохранённых `suppliers_search` и `candidates` без `relevance` по умолчанию
используется `layout=matches`; новым запускам этот формат доступен явно. Первые столбцы совместимы с «Поставщиками»:
`lot_id;supplier_inn;supplier_kpp;is_winner`, далее `target_lot_id`, идентификаторы целевого
извещения и сведения о совпадении/источнике. Одна строка — одна связь участия с целевым
извещением; поэтому ИНН в плоском CSV повторяется для разных связей. Неизвестные значения
пустые, флаги `true/false`, вложенные сведения сериализованы в JSON. Полей score/rank/бонусов
нет. Поисковая фраза доступна в `search_query`. Любой запуск кандидатов можно выгрузить
в другом виде через `/runs/{id}/export?layout=pool` или `?layout=matches`.
Формулы экранируются, ИНН/КПП в Excel импортируйте как текст.

Число запросов, результатов поиска, загруженных страниц и время ожидания ограничены
настройками (`MAX_QUERIES_PER_ITERATION`, `SEARCH_RESULT_LIMIT`, `MAX_PAGES_PER_LOT`).
Это лимиты получения источников, а не ограничения длины экспортируемого списка.
Ошибка Ollama на одной странице не останавливает остальные страницы и извещения.
После каждого извещения сохраняются найденные кандидаты, источники и статистика.
Ошибки/достигнутый лимит страниц отмечаются как `search_stats[].status=partial` и
предупреждения в `run.warnings`; отключённый веб-поиск — `unavailable`. Сам запуск
может иметь `status=completed` при частичных результатах. `candidates_found` считает
только уникальные ИНН из веб-поиска данного извещения; исторические совпадения находятся
в общем `candidates`. `observed_at` — время получения страницы, а не дата обновления
сведений компанией. Страницы без цитируемого ИНН не добавляются.

Старые запуски автоматически не пересчитываются: для сбора по всем извещениям после
исправления ранней остановки нужен новый `POST /suppliers/bulk`.

Результаты сохраняются отдельно в `candidate_search_results`; старые запуски и таблицы
рейтинга не меняются. При `AUTO_CREATE_TABLES=true` новая таблица создаётся при старте.
Для БД под управлением Alembic выполните `python -m alembic upgrade head` (миграция
`0002_candidate_search`). Однофайловый вызов через `file` сохраняет прежнее поведение
и прежний формат результата. При наличии `tru` поле `file` также может
служить альтернативным именем для `notices`.

## Проверка через API

В другом терминале PowerShell из корня проекта:

```powershell
$created = curl.exe -s -X POST "http://127.0.0.1:8000/runs" -F "file=@data/sample_procurement.json" | ConvertFrom-Json
$runId = $created.run_id
Invoke-RestMethod "http://127.0.0.1:8000/runs/$runId"
```

`POST /runs` отвечает HTTP 202 и `{ "run_id": 1, "status": "pending" }`.
Фоновая обработка меняет статус на `processing`, затем `completed` или `failed`.
Короткое demo может завершиться до первого запроса статуса.

```powershell
do {
    $run = Invoke-RestMethod "http://127.0.0.1:8000/runs/$runId"
    $run | Select-Object id, status, stage, progress, error
    if ($run.status -in @("pending", "processing")) { Start-Sleep -Seconds 1 }
} while ($run.status -in @("pending", "processing"))

Invoke-RestMethod "http://127.0.0.1:8000/runs/$runId/results" | ConvertTo-Json -Depth 20
curl.exe -f "http://127.0.0.1:8000/runs/$runId/export" -o "results-$runId.csv"
```

CSV содержит UTF-8 BOM для Excel; формулы из внешних строк экранируются.
Столбец ИНН импортируйте в Excel как текст, чтобы сохранить ведущие нули.

| Маршрут | Результат |
| --- | --- |
| `POST /runs` | Multipart-поле `file`, CSV/JSON; постановка в фон |
| `GET /runs/{id}` | Статус, этап, прогресс, ошибка и предупреждения |
| `GET /runs/{id}/results` | Лоты, требования, компании, проверки, факты и источники |
| `GET /runs/{id}/export` | CSV завершённого запуска; иначе 409 |
| `GET /health` | Доступность API и активные режимы |

Промежуточные результаты доступны с текущим `run.status`; завершённость проверяйте
по статусу запуска. Неверный формат загрузки даёт 415, пустой файл — 422,
превышение лимита — 413, неизвестный run — 404. Синтаксическая/структурная ошибка
в содержимом файла переводит уже созданный запуск в `failed`.

## Формат закупки

Основной формат JSON:

```json
{
  "lots": [{
    "external_id": "lot-1",
    "name": "Промышленные электрические плиты",
    "description": "Оборудование для пищеблока",
    "okpd2": "27.51.28.130",
    "quantity": 3,
    "budget": 450000,
    "requirements": [{
      "name": "Опыт работы от пяти лет",
      "fact_type": "experience_years",
      "type": "number",
      "operator": "gte",
      "expected_value": 5
    }]
  }]
}
```

`fact_type` связывает требование с одноимёнными фактами. Типы: `number`, `date`
(ISO `YYYY-MM-DD`), `boolean`, `enum`, `text`. Операторы: `eq`, `ne`, `gte`, `lte`,
`gt`, `lt`, `contains`, `in`; совместимость типа и оператора валидируется.
Для `in` передавайте массив допустимых строк; boolean — JSON `true`/`false`.
Числа должны быть конечными. Единицы измерения должны совпадать: автоматического
перевода мощности, размеров и валют нет.

CSV: одна строка — один лот. Колонки `name,description,okpd2,external_id,quantity,budget,requirements`;
обязательна `name`. В `requirements` можно передать JSON-массив с корректным CSV-экранированием.
Готовые примеры находятся в `data/`. XLSX и OCR в текущем MVP не поддерживаются.
ИНН и коды в исходных данных храните строками.

Если структурированных требований нет, LLM при включении может извлечь их из
описания. При недоступной модели поиск продолжается, предупреждение указывает
на отсутствие проверок. Без требований score=0 и coverage=0: это результаты
поиска, а не подтверждённое соответствие.

## Архитектура и pipeline

```text
app/
  main.py, config.py, database.py
  api/           REST и зависимости запроса
  models/        SQLAlchemy: Run, Lot, Requirement, Company, факты и результаты
  schemas/       Pydantic-контракты API и сервисов
  repositories/  сохранение и загрузка данных
  services/      parser, history_search, web_search, fact_extractor,
                 supplier_extractor, classification, company_merger,
                 requirement_checker, ranking, exporter
  agent/         pipeline.py, ollama_client.py, prompts.py
alembic/         версия схемы БД
data/            вымышленные демонстрационные данные
tests/           сервисные, интеграционные и API-тесты
scripts/         проверка запущенного сервера по HTTP
```

Точка входа — `ProcurementPipeline.run(run_id)` в `app/agent/pipeline.py`:

1. Прочитать файл и проверить структуру лотов и требований.
2. При отсутствии ОКПД2 предложить код по истории, затем найти кандидатов по ОКПД2 и TF-IDF без LLM.
3. Найти страницы через `WebSearchProvider` и извлечь факты с цитатами.
4. Объединить кандидатов, сохранив все доказательства.
5. Проверить требования обычным Python-кодом.
6. При избытке `unknown` выполнить уточняющий поиск в пределах лимитов.
7. Рассчитать рейтинг и сохранить результаты по лоту.

Долгие сетевые вызовы выполняются без открытой транзакции БД. CPU-этап TF-IDF
вынесен из event loop. Один локальный pipeline обрабатывает один run за раз;
другие запуски остаются `pending`. `BackgroundTasks` работает в процессе API.
При остановке процесса незавершённые задания не возобновляются: следующий старт
помечает их `failed/interrupted`. Повторите загрузку файла. `--reload` также
прерывает обработку при изменении кода. Для защиты используйте запуск без `--reload`.

БД хранит исходный файл в base64 в Run для небольших MVP-загрузок. Факты привязаны
к компании, запуску и лоту, чтобы результаты одного запуска не менялись от другого.
API не держит сессию БД общей с фоновой задачей. Несколько API workers и несколько
одновременно работающих инстансов в этой версии не поддерживаются.

## История, факты и рейтинг

История загружается из `data/history.csv`; путь меняется через `HISTORY_PATH`.
Поля: `lot_name,description,okpd2,company_name,company_inn,company_website`.
Дополнительно: `lot_id` для идентификации исторической закупки и `is_winner`
со значением `true`/`false`. Если признака победы нет, победа не предполагается.
Историческое участие не доказывает исполнение контракта или наличие товара.
Условные `history://` ссылки обозначают локальные записи, `demo://` — demo-источники.

При объединении приоритет у ИНН, затем домена и нормализованного названия.
Разные известные ИНН запрещают объединение через более слабый признак.
Каждый факт содержит `source_url`, `source_quote`, `source_title`, `source_kind`,
`is_demo`. Цитата модели проверяется по исходному тексту. Это проверяет наличие
цитаты, но не гарантирует правдивость сайта и корректность интерпретации моделью.

Проверки имеют ровно три состояния: `confirmed`, `contradicted`, `unknown`.
Пропуски, неподдерживаемые значения и конфликтующие свидетельства дают `unknown`.
`coverage = (confirmed + contradicted) / total`: это покрытие проверками,
а не доля выполненных требований.

Веса задаются конфигурацией: confirmed=1, contradicted=-2, unknown=0.
Средний вес линейно нормализуется между минимальным и максимальным весами:

```text
raw = (confirmed*w_confirmed + contradicted*w_contradicted + unknown*w_unknown) / total
score = 100 * (raw - w_contradicted) / (w_confirmed - w_contradicted)
```

Это `base_score`. За подтверждённые победы в сопоставимой истории добавляется
`history_bonus`: по умолчанию 2 балла за уникальную закупку, максимум 5 баллов,
с ограничением итогового score до 100. Веб-утверждение «мы победители» не даёт бонуса.
При одинаковом `lot_id` повторные строки не увеличивают число побед.
Поля `base_score`, `history_bonus`, `history_wins` возвращаются отдельно и входят в CSV.

При стандартных весах все `unknown` без бонуса дают **66.67 при coverage=0**.
Это нейтральный индекс, **не вероятность соответствия и не подтверждённая рекомендация**.
Всегда показывайте score вместе с проверками и coverage. TF-IDF используется для
поиска кандидатов и разрешения равенства рейтингов. Формула не оценивает юридическую
допустимость участия; обязательные ограничения требуют отдельного решения заказчика.

## Соответствие цепочке из десяти шагов

| Шаг | Реализация | Граница MVP |
| --- | --- | --- |
| 1. Понимаем, что хотят купить | `procurement_parser.py`: лоты, описания, требования | CSV/JSON; свободные требования — локальная LLM |
| 2. Определяем товар/услугу и ОКПД2 | Название/описание лота + `classification.py` | Код из входа сохраняется; отсутствующий предлагается по похожей истории |
| 3. Ищем похожие закупки | `history_search.py`: ОКПД2 и TF-IDF | История должна быть подготовлена в указанном формате |
| 4. Находим участников | Исторические строки связаны с компаниями | Участие не доказывает исполнение |
| 5. Учитываем победителей | Исторический `is_winner`, отдельный ограниченный бонус | Без признака победы бонуса нет |
| 6. Ищем в интернете | Интерфейс провайдера, demo/Brave | Demo офлайн; реальные запросы требуют собственного ключа |
| 7. Собираем информацию | `fact_extractor.py`, цитаты и источники | Реальные страницы извлекаются через локальную Ollama |
| 8. Проверяем требования | `requirement_checker.py` | confirmed / contradicted / unknown; единицы должны совпадать |
| 9. Считаем рейтинг | `ranking.py` | Детерминированная формула, все составляющие видны |
| 10. Показываем кандидатов и доказательства | `/results`, `/export`, Swagger | Пользовательский frontend подключается к REST API |

ОКПД2, подобранный автоматически, обозначается `okpd2_source="history"`; API
возвращает `okpd2_similarity` и источник с цитатой. Это сходство текста,
не вероятность правильности кода. Подбор использует минимальный порог сходства
и отрыв от альтернативной категории (`OKPD2_MIN_SIMILARITY`, `OKPD2_MIN_MARGIN`).
При слабом или неоднозначном совпадении код остаётся неизвестным, текстовый поиск
продолжается. Полного официального классификатора в проекте нет: предложенный код
нужно проверять. Код, предоставленный пользователем, помечается `input`.

## Локальная Ollama

Установите Ollama для Windows с https://ollama.com/download/windows.
В отдельном терминале, если служба ещё не запущена:

```powershell
ollama serve
```

Затем загрузите модель:

```powershell
ollama pull qwen2.5:7b
```

Измените `.env`:

```dotenv
LLM_ENABLED=true
OLLAMA_URL=http://localhost:11434
OLLAMA_MODEL=qwen2.5:7b
```

Клиент вызывает локальный `/api/chat`, передаёт JSON Schema из Pydantic и
валидирует ответ. Число повторов и timeout ограничены. LLM используется для
языковых задач, а не вычисления рейтинга, сравнения чисел или объединения ИНН.
Неизвлечённые сведения остаются неизвестными; LLM не является источником.
Размер модели выбирайте под доступную память. Живой вызов требует установленного
Ollama и загруженных весов; demo работает без них.

## Настоящий интернет-поиск

Интерфейс `WebSearchProvider.search(query)` находится в `app/services/web_search.py`.
Реализация возвращает `SearchResult`, после чего общий `fact_extractor` получает
страницу и извлекает сведения. Новый провайдер подключается через
`create_web_search_provider(settings)`; остальные этапы менять не нужно.

Встроены `demo`, `disabled`, Brave Web Search и SearXNG. Brave требует ключ и
платёжный профиль; по FAQ Brave, кредитная карта нужна даже для активации плана с
бесплатными ежемесячными кредитами ([условия Brave](https://api-dashboard.search.brave.com/documentation/resources/help-feedback)).
Если не хотите вводить карту, можно запустить собственный бесплатный экземпляр
SearXNG и подключить его без API-ключа:

```dotenv
WEB_SEARCH_PROVIDER=searxng
SEARXNG_URL=http://localhost:8080
LLM_ENABLED=true
```

SearXNG — самостоятельный метапоисковик с открытым кодом. Установите Docker Desktop,
затем разверните SearXNG по [официальной инструкции Docker Compose](https://docs.searxng.org/admin/installation-docker.html).
В его `settings.yml` проверьте, что включён JSON-формат (сохраните остальные
настройки `search`):

```yaml
search:
  formats:
    - html
    - json
```

Запустите SearXNG командой `docker compose up -d` в каталоге его Compose-файлов.
Убедитесь, что адрес `http://localhost:8080` открывается. SearXNG API возвращает
результаты по `/search?q=...&format=json`; доступность JSON зависит от настроек
экземпляра ([описание Search API](https://docs.searxng.org/dev/search_api.html)).
Затем задайте параметры в `.env` самого Procurement Scout и перезапустите API.
При поиске по реальным сайтам `LLM_ENABLED=true` и работающая локальная Ollama
нужны для извлечения фактов со страниц. Проверьте режим через `GET /health`,
запустите поиск через Swagger (`POST /runs`) и откройте `GET /runs/{id}/results`:
там будут найденные поставщики, ссылки и источники подтверждённых фактов.

Оплата API и карта для SearXNG не требуются, но фактические поисковые движки могут
ограничивать частоту запросов или временно блокировать обращения. Свой экземпляр
даёт контроль над конфигурацией, но не гарантирует полноту или актуальность выдачи.
При недоступном поиске сохраняются результаты истории и предупреждение.
Для извлечения сведений с произвольных реальных сайтов нужна локальная Ollama.
HTML обрабатывается без JavaScript-браузера; динамические страницы могут дать
мало текста. Размеры страниц, время запросов, итерации и число источников ограничены.
Сборщик отклоняет локальные/частные адреса; модель работает с уже полученным текстом.

## Строгий контракт извлечения со страниц поставщика

`app/services/supplier_extractor.py` принимает уже скачанные страницы одного
известного сайта компании. Этот модуль не ищет и не скачивает информацию.
`fact_extractor.py` отвечает за загрузку и адаптацию результата к pipeline.
Существующий pipeline передаёт по одной странице; многостраничный интерфейс
доступен сборщику через `extract_supplier(pages, website_url, ...)`.

```python
from app.schemas.supplier import DownloadedPage
from app.services.supplier_extractor import extract_supplier

pages = [
    DownloadedPage(
        url="https://company.example/catalog", title="Каталог",
        clean_text='ООО "Альфа". Поставляем центробежные насосы.',
    ),
    DownloadedPage(
        url="https://company.example/delivery", title="Доставка",
        clean_text="Осуществляем поставки по всей России.",
    ),
]
supplier = await extract_supplier(pages, "https://company.example")
```

LLM получает блоки `SOURCE_URL`, `PAGE_TITLE`, `TEXT` с разделителем `=== PAGE ===`.
Единственный контракт ответа — `LLMExtractionResult`:

```json
{
  "company_name": null,
  "address": null,
  "facts": []
}
```

Факт содержит ровно `type`, `value`, `source_url`, `source_quote`.
Допустимые типы: `product`, `service`, `region`, `certificate`, `license`,
`specialization`. Значение и цитата ограничены 500 символами. Дополнительные поля,
старый формат ответа, неизвестные типы, Markdown и пояснения не проходят
Pydantic-валидацию. В Ollama передаётся JSON Schema этого же контракта.
Пустой результат допустим. ИНН, телефон, email, рейтинг и отдельные массивы
products/services/regions модель не возвращает.

После валидации формы Python принимает факт только при точном совпадении URL
с переданным источником и дословном наличии цитаты в `TEXT` именно этой страницы.
Проверка выполняется до нормализации; URL и цитата не исправляются.
Для `value` убираются лишние пробелы; одинаковые `(type, value без учёта регистра)`
объединяются с сохранением первого подтверждённого источника. Цитата остаётся
дословной, включая внутренние пробелы и переносы строк.

Название и адрес, отсутствующие в переданном `TEXT`, заменяются на `null`:
заголовка или домена для их подтверждения недостаточно. Модель должна выбирать
основной явно обозначенный адрес и возвращать `null` при неоднозначности.
Присутствие цитаты проверяет происхождение текста, но не гарантирует правильность
его смысловой интерпретации, принадлежность упомянутых сведений компании или
действительность сертификата. Упоминание товара в статье, адрес офиса и общие
рекламные заявления не должны превращаться в доказательство поставок/сертификации.

Общий лимит текста для одного вызова — 30 000 символов; проверяются только те
фрагменты, которые действительно получила модель. При совпадающем URL и разных
текстах вход отклоняется. Сниппеты поиска не используются как доказательства.

Обычный код извлекает явно подписанные ИНН, телефоны и email либо получает их
через `DeterministicSupplierData`. Несколько различных значений дают `None`;
ИНН проверяется по формату (10/12 цифр, не все нули), без проверки контрольной
суммы или регистрации. Текст footer сохраняется для реквизитов. При недоступной
или выключенной модели `extract_supplier` сохраняет эти контакты, возвращая
пустые семантические поля.

Результат `SupplierParsedData` содержит name/inn/website/phone/email/address и
проверенные facts. products/services/regions вычисляются Python только из этих
facts. В `/results` и CSV он доступен в поле `supplier_data`, привязанном к снимку
результата конкретного запуска. `supplier_data.website` — адрес сайта переданных
страниц. Домен произвольного результата поиска, например агрегатора, не
присваивается верхнему `CompanyCandidate.website` и не используется для слияния
компаний; принадлежность официального сайта требует отдельного подтверждения.
Кандидат без подтверждённого названия в текущую
выдачу не добавляется, даже если низкоуровневый парсер сохранил контакты.

Новые веб-факты сохраняют шесть указанных типов. Для проверки текстовых
требований используйте соответствующий `fact_type`, например `product` и
оператор `contains`. Для этих типов `eq`, `contains`, `in` проверяют наличие
подходящего значения среди положительных фактов: разные товары/услуги не
считаются конфликтом. Отсутствие совпадения даёт `unknown`, поскольку перечень
может быть неполным; отрицания и булевы свойства из него не выводятся.
`certificate` не преобразуется автоматически в
`iso9001=true`, а география деятельности `region` — в обещание доставки.
Числовой стаж и другие отсутствующие в этом контракте сведения остаются
`unknown`, если их не подтвердил отдельный источник. Сопоставление сертификатов
и условий поставки требует отдельной предметной проверки.
Старые demo-факты и исторические факты обрабатываются обычным кодом;
демо-фикстуры не являются альтернативным форматом ответа LLM.

## Alembic и PostgreSQL

Для чистой БД можно управлять схемой только через миграции:

```powershell
$env:AUTO_CREATE_TABLES = "false"
.\.venv\Scripts\python.exe -m alembic upgrade head
.\.venv\Scripts\python.exe -m uvicorn app.main:app
```

Если таблицы уже создал первый запуск приложения, первоначальную миграцию
повторно выполнять нельзя. Для **неизменённой начальной схемы этого проекта**:

```powershell
.\.venv\Scripts\python.exe -m alembic stamp head
```

После дальнейших изменений моделей создавайте и проверяйте миграции;
`create_all` не обновляет существующие таблицы.

Для PostgreSQL создайте пустую базу и измените только строку подключения:

```dotenv
DATABASE_URL=postgresql+asyncpg://user:password@localhost:5432/procurement
```

Драйвер asyncpg уже входит в зависимости. Для новой базы примените `alembic upgrade head`.
Переключение URL меняет хранилище, но **не переносит данные** из старого SQLite.
Пароли со специальными символами в URL должны быть percent-encoded.

## Проверка проекта

```powershell
.\.venv\Scripts\python.exe -m pip check
.\.venv\Scripts\python.exe -m pytest -q
.\.venv\Scripts\python.exe -m compileall -q app
```

Для повторения именно проверенных версий используйте
`pip install -r requirements.lock.txt` в чистом Python 3.12 окружении.
После запуска сервера можно проверить весь демонстрационный сценарий по HTTP:

```powershell
.\.venv\Scripts\python.exe scripts/smoke_test.py
```

Тесты используют временные базы и локальные данные. Они проверяют дедупликацию,
типизированные требования, рейтинг, историю, некорректные ответы модели,
провалы внешних источников, изоляцию данных, REST API и CSV. Доступ к реальным
платным сервисам для запуска тестов не нужен.

Это локальный MVP без аутентификации. Для демонстрации запускайте на 127.0.0.1;
публичное размещение потребует контроля доступа и надёжного фонового worker.
